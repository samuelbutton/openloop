# T4: recorded tabular benchmarks

Implemented on October 12, 2026. Needs: [N2, N4, N9](../NEEDS.md#n1n10).
`NASBench201` and `HPOB` implement the same workload contract as T0 and T1.
Use them with `ExperimentEnv` and the public ledger API.
They perform CPU lookups. They do not train models or download files.

The [download manifest](../data/tabular/manifest.json) fixes local artifact hashes.
Each loader checks its selected file before use. The NAS loader also checks the
official release hash before legacy pickle loading. It checks the recorded API
and PyTorch versions, then hashes the installed API source files.
HPO-B JSON lookups use the standard library and require no optional dependency.
Imports and constructors from an existing `RecordedTable` need no benchmark packages.

## Contract and work

| Workload | Mutable setting | Fidelity | Work charged | Score, maximized |
| --- | --- | --- | --- | --- |
| NAS-Bench-201 | `architecture_index` | `12`, `200` | 12 or 200 benchmark epochs | Validation accuracy, percent |
| HPO-B | `configuration_index` | `lookup` | One lookup | Task-normalized response in [0, 1] |

The task, dataset, candidate features, source artifact, dependencies, and scoring
rule are frozen for each workload. Candidates cannot change them or supply a score.
Only the table index is mutable. `candidates` returns immutable architecture
strings or feature vectors in the original index order. It returns no scores.

The trusted evaluator gets the authoritative score from its own immutable table.
It rejects candidate programs, forged scores, wrong work amounts, missing seeds,
and altered input manifests. `validation_score` has sample count 1.
It is one recorded outcome, not a mean over benchmark seeds.
Input hashes include the complete derived table, task, seed, fidelity, and phase.
Candidate identities include the task and its candidate space, so index 0 in two
HPO-B tasks cannot collide. Table row ordering does not change its content hash.

The specification declares deterministic reproducibility. The same lookup returns
the same recorded score. A cache hit references the same attempt and charges no
additional work. An explicit replication can repeat the lookup, but it does not
create an independent training measurement. Allocator loop seeds belong to the
allocator; they are not additional benchmark training seeds.

NAS epoch work is benchmark accounting. A 200-epoch request charges 200 epochs,
even after a 12-epoch request. The two recorded training runs are independent;
the adapter does not claim to resume the 12-epoch run. HPO-B has no recorded
multi-fidelity training axis, so the adapter declares only one fidelity.

`lookup_seconds` records the local adapter's measured lookup and contract-check
duration. NAS also reports `recorded_training_seconds` when the table provides it.
That value is historical benchmark training time. It is not local elapsed time
or money spent by this lookup. HPO-B does not invent missing training costs.

## NAS-Bench-201

Load the [verified v1.1 artifact](../data/tabular/README.md#nas-bench-201) once:

```python
from pathlib import Path
from openloop.loops import NASBench201

loop = NASBench201.load(Path("data/tabular"))
screen_seed = loop.seeds(0, fidelity="12")[0]
full_seed = loop.seeds(0, fidelity="200")[0]
```

The default dataset is `cifar10-valid`. `cifar100` and `ImageNet16-120` are also
accepted. The [official API](https://github.com/D-X-Y/NAS-Bench-201) distinguishes
`x-valid` from test scores. The adapter queries only `x-valid` and training time.
It never calls `get_more_info`, which can also read test metrics.
The artifact itself includes test records. Loading it is not a file-access sandbox.

An action seed must be an exact recorded training seed. No seed is drawn, remapped,
or averaged. The release records different seed sets at 12 and 200 epochs.
For architecture 0 on CIFAR-10, the checked screen seed is 111 and the checked
full seed is 777. The two fidelities are independent training runs, so they are
not seed-paired: a seed at 12 epochs is not the same random stream at 200 epochs.
Do not treat equal seed numbers as a paired design.
Call `seeds` for each candidate and fidelity before constructing actions.

The initial official API load is large. It materializes all 15,625 architectures.
The adapter then retains only immutable validation scores, candidate strings,
recorded seeds, and available training times. Later lookups use a dictionary,
and `seeds` reads a map built once per table.

The loaders cache per verified artifact. A table is keyed by the artifact path, its
SHA-256, and the dataset or task, so a second `load` of the same task returns the
same immutable table without reading the 5 GB file again. A file whose size,
modification time, and inode are unchanged is not hashed again; any change to one
of them forces a new hash and a rejected load if the content differs. The HPO-B
loader keeps the most recent parsed meta-split (124 to 346 MB of JSON, several
times that in memory), so loading several tasks from one split parses it once.
The cache is per process. `openloop.loops.tabular_loaders.clear_caches()` empties it.
Loading the held-out table of a NAS dataset reads the artifact again, because the
cache keeps tables, not the 9 GB API object.

## HPO-B

```python
from pathlib import Path
from openloop.loops import HPOB

loop = HPOB.load(Path("data/tabular"), "4796", "31")
```

This selects one task from the original meta-validation file. `split="train"`
selects the original meta-train file. The API rejects `split="test"`.
It opens no meta-test, augmented-train, or initialization file.
The meta-split describes the task's role in optimizer development, not a new
train/validation split inside its recorded response table.

The [official HPO-B protocol](https://github.com/machinelearningnuremberg/HPO-B)
normalizes each task with `(y - min(y)) / (max(y) - min(y))`.
The adapter uses that same formula and preserves row indices and feature vectors.
It rejects constant-response tasks because that formula has a zero denominator.
The authoritative lookup seed is 0; other action seeds are rejected.
The five published initialization seeds define optimizer starting sets. They
are not repetitions of model training. Initialization and suggestion policies
belong to the allocator/proposer layer and are not implemented by this adapter.

## Run through the Env

```python
import asyncio
from pathlib import Path
from openloop.ledger import Ledger, content_hash
from openloop.loops import HPOB, ExperimentEnv, LoopAction

async def query(ledger: Ledger) -> None:
    loop = HPOB.load(Path("data/tabular"), "4796", "31")
    env = ExperimentEnv(
        loop, ledger, runner=loop.run,
        config={"configuration_index": 0},
        environment_hash=content_hash({"purpose": "documented lookup example"}),
        budget=2,
    )
    measured = await env.step(LoopAction(0))
    cached = await env.step(LoopAction(0))
    assert measured.executed
    assert not cached.executed
    assert cached.attempt_id == measured.attempt_id

# Choose a new ledger path for a real run.
with Ledger(Path("t4-example.sqlite3")) as ledger:
    asyncio.run(query(ledger))
```

Real campaigns must hash their actual environment. This example identity describes
only the example's purpose. The evaluator is a trusted adapter; private attributes
and locally readable benchmark files are not an oracle security boundary.
Held-out evaluation after selection closes is a separate guarded operation,
described next.

## Held-out evaluation

Selection phases see only validation scores. `NASBench201`, `HPOB`, and
`TabularLoop` reject any table that carries a held-out score split, and
`NASBench201.load` and `HPOB.load` cannot produce one. A held-out table comes only
from the separately named loaders, and only `HeldOutEvaluator` consumes it.

| Workload | Selection score | Held-out score | Held-out loader |
| --- | --- | --- | --- |
| NAS-Bench-201 `cifar10-valid` | `x-valid` | `ori-test` | `load_nas201_held_out` |
| NAS-Bench-201 `cifar100`, `ImageNet16-120` | `x-valid` | `x-test` | `load_nas201_held_out` |
| HPO-B | meta-validation (or meta-train) | meta-test | `load_hpob_held_out` |

`HeldOutEvaluator(table, selection, ledger, baseline=..., candidates=...)` is a
decider `FinalEvaluator`: pass the instance to `Campaign.finalize`. The caller maps
each protocol candidate hash to its configuration; the constructor checks that each
hash matches its configuration. Build the held-out `StagePlan.template` with
`evaluator.baseline_template(environment_hash=..., fidelity=...)`, with a metric
whose split is `held_out`. For each held-out seed the evaluator runs the baseline
and the selected candidate, writes ledger runs in phase `held_out`, and returns
`Pair`s. The first call consumes its permission, and a repeated seed raises instead
of returning a cache alias. The held-out loop adopts the selection loop's candidate
identity, so it requires identical candidate lists and, for NAS, the same dataset
and artifact. Its data hash is the held-out table's, so the protocol's check that
held-out data differs from selection data holds.

Weaker separation for two datasets: in NAS-Bench-201, `x-valid` and `x-test` of
`cifar100` and `ImageNet16-120` are the two halves of the original test set. Held-out
scores there are therefore not drawn from data fully separate from the selection
scores. Only `cifar10-valid` has a selection split (`x-valid`, part of the
original training data) that is disjoint from its held-out `ori-test` set.
Treat held-out results on the other two datasets as a weaker check.

HPO-B meta-test tasks are different tasks from the validation tasks. The evaluator
accepts a meta-test table only when its candidate vectors equal the selection
task's, which meta-test tasks rarely satisfy. Held-out evaluation of a candidate
configuration across HPO-B tasks is therefore not implemented. The loader and the
guard exist, and they are tested with fixtures.

The tests use small fixtures. They check that the validation path never requests a
held-out set, that each dataset queries the right held-out set, and that the
evaluator reads once. No test or code path here has opened the real `ori-test`,
`x-test`, or meta-test data. The NAS artifact contains those records, and
`data/tabular/hpob/hpob-data/meta-test-dataset.json` is already present, so
nothing needs downloading. To provision another machine, follow
[data/tabular/README.md](../data/tabular/README.md#reproduce): download and extract
both archives, verify `downloads.sha256`, and keep the manifest entries
(`downloads` for the NAS file, `hpob_extracted_files` for `meta-test-dataset.json`).
The loaders refuse any file whose size and SHA-256 differ from the manifest.
Isolating held-out files from candidate code is the host's job.

## Checks and evidence

[Offline tests](../tests/loops/test_t4.py) cover both contracts, exact recorded
seeds, cache reuse, historical costs, immutable identities, hash-order invariance,
invalid tables, failed attempts, score forgery, and rejection of unverified pickle.
An API stand-in rejects any request for test metrics on the selection path. Further
tests cover the held-out loaders, the evaluator, and the loader caches.

The read-only [smoke runner](../research/probe_t4.py) exercises real downloaded
tables through `ExperimentEnv`, final scoring, and a temporary ledger. It checks
cache reuse and writes a new receipt without overwriting earlier evidence:

```sh
uv run --group benchmarks python research/probe_t4.py nas201 \
  --output /tmp/t4-nas201-new.json
uv run python research/probe_t4.py hpob \
  --output /tmp/t4-hpob-new.json
```

[NAS receipt](../research/t4/nas201-smoke-2026-10-12.json) and
[HPO-B receipt](../research/t4/hpob-smoke-2026-10-12.json) record the checked task
identities, results, cache hits, and stage timestamps. These checks are integration
checks, not allocator performance results. Other NAS datasets and all HPO-B tasks
have not been exercised through these adapters.
