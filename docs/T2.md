# T2: local GRPO on verifiable arithmetic

Implemented on October 15, 2026. Supports N1, N2, N4, and N9 in [NEEDS.md](../NEEDS.md).
[T2](../src/openloop/loops/t2.py) uses the existing `ExperimentEnv`, ledger,
request keys, explicit replications, failure records, and lineage. It reuses the
same executor and GPU lane as T1 and T3. No new ledger schema is needed.

## Frozen starting recipe

The native model is
[Qwen2.5-0.5B-Instruct-4bit](https://huggingface.co/mlx-community/Qwen2.5-0.5B-Instruct-4bit/tree/53a32aee5e9447773fd2b85988395066aef3700a),
pinned to revision `53a32aee5e9447773fd2b85988395066aef3700a`.
The [local snapshot](../research/t2/model-snapshot.json) records every model and
tokenizer asset hash. The snapshot hash is
`0a09499476a2856b08f298c4382047e6b9185ea00a9c4b893462652d2dd941fb`.
The weights are ignored local assets. They are not included in the repository.

The actor uses 4-bit base weights and rank-8 Q/V LoRA on the last four layers,
scale 1, dropout 0. A separate frozen quantized base supplies reference
probabilities. Training uses the frozen chat template. Prompt length is capped
at 128 tokens. Actor log probabilities are recomputed before the update under
the unchanged policy, using the same causal scoring path as the gradient loss.
This avoids treating cached-generation rounding as a policy change.

| Mutable setting | Default | Limit |
| --- | ---: | --- |
| Learning rate | 0.0001 | Finite and positive |
| KL beta | 0.04 | Finite and nonnegative |
| Rollout group size | 4 | 2–8 |
| Maximum new tokens | 64 | 1–256 |

Model bytes, LoRA configuration, clip epsilon (0.2), reward code, data,
tokenizer, and evaluation rules are frozen. Each fresh group gets exactly one
optimizer step scored against the unchanged policy, so the PPO ratio is 1 and the
clip never binds. All other settings are refused. See the
[training interface](TRAINING.md) for loss and optimizer semantics.

Each update uses one training expression and a fresh rollout group. Advantages
are standardized within that prompt's group. Equal-reward groups have zero
policy advantages; the implementation does not invent a learning signal.
KL regularization can still contribute a gradient after an earlier policy change.

## Tasks, fidelity, and scoring

The [arithmetic source](../src/openloop/training/grpo.py) defines integer addition,
subtraction, and multiplication on operands 0–19. Content-hash buckets select
64 training expressions and 16 validation expressions in stable order. Train
and validation are disjoint. Twenty percent of the expression space is reserved;
this is not an implemented sealed held-out dataset or evaluator.

The prompt asks for just the integer result. The trusted reward accepts a
complete signed integer response with optional surrounding whitespace. It
rejects equations, code, explanations, and trailing text. It never evaluates
generated Python. Reward is 1 for the exact answer and 0 otherwise.

`smoke` uses 2 optimizer updates; `short` uses 8. The work unit is
`optimizer_updates`, not tokens. EOS makes generated lengths variable. The
worker records actual generated and gradient-target tokens and enforces the
recipe's maximum generation envelope. Candidates with different group sizes or
generation limits are not equal-token comparisons merely because updates match.

Validation runs once after training: one greedy completion per frozen validation
task. The metric is `pass_rate`, a fraction to maximize, with the number of
validation tasks recorded. Inner tasks are not independent training seeds.
No validation task enters a gradient batch. No held-out score is produced.

Each job reloads the same base and initializes its LoRA at the declared seed.
There is no implicit warm start from a preceding ledger run. The saved checkpoint
is an output, not an automatic parent checkpoint. The ledger records model,
recipe, dependency-lock, tokenizer, data, evaluator, seed, phase, and fidelity
identities. Cache aliases do not count as additional trials.

## Run setup

Download the pinned public assets explicitly, without authentication or training:

```sh
uv run python -m openloop.training.prepare_model \
  --output research/t2/models/qwen2.5-0.5b-4bit \
  --manifest /tmp/t2-model-snapshot.json
```

Use a new manifest destination. The downloader refuses to replace a freeze record.
The worker verifies local asset bytes and installed packages against the supplied
`uv.lock`. It loads local files only and disables remote code. The trusted local
executor is not a filesystem or network sandbox. No hosted service is called.

Prepare a concrete engineering plan before explicitly executing it:

```sh
uv run python -m openloop.studies.t2_smoke \
  --model-manifest research/t2/model-snapshot.json \
  --plan /tmp/t2-smoke-plan.json --output /tmp/t2-new-run
# After reviewing and authorizing that local GPU workload:
uv run python -m openloop.studies.t2_smoke \
  --model-manifest research/t2/model-snapshot.json \
  --plan /tmp/t2-smoke-plan.json --output /tmp/t2-new-run --execute
```

The native worker has a 30-minute process wall limit, 16 GiB sampled resident-RAM
limit, and 16 MiB per log stream. The RAM sample excludes Metal allocations.
GPU admission uses the existing shared lane. Queue time is separate from the wall
limit. Cancellation stops the worker process group. A new run uses a new isolated
ledger and retains logs, source bytes, model/optimizer checkpoint, and a typed
report. Held-out isolation and scientific S6 execution remain separate tasks.

## Native evidence and correction

Two-update engineering smokes ran on the local M4 Pro on October 15, 2026.
The [first report](../research/t2/run-smoke-2026-10-15/report.json) scored 0/16.
Its tag-only answer format rejected even a correct bare integer. The
[diagnostic](../research/t2/diagnostic-2026-10-15.json) records those answers.
That report, its plan, source bytes, and ledger remain unchanged.

The corrected plain-integer recipe's
[current report](../research/t2/run-smoke-2026-10-15-namespaced/report.json) records
2 updates, 8/16 validation passes, mean rollout reward 0.5, no uniform-reward
groups, and maximum gradient norm 0.6958. It generated 111 returned tokens
including evaluation and used 42 completion targets for gradients. The worker
process took about 3.68 seconds; training took about 0.74 seconds and validation
about 0.45 seconds. The mixed rewards supplied nonzero policy advantages.
These are one warm engineering sample, not steady-state throughput estimates.
Returned-token counts include EOS and exclude unused mlx-lm prefetch.

The [earlier corrected smoke](../research/t2/run-smoke-2026-10-15b/report.json) and
[receipt-check repeat](../research/t2/run-smoke-2026-10-15-final/report.json)
also remain available. Review then found overlapping random-key streams between
groups in the MLX sampler. A public-API regression reproduced the problem; the
current implementation derives namespaced request/sample seeds and splits token
keys instead of adding offsets. The namespace also separates sampling from model
initialization. Per-update request seeds are hashed from the job seed and update
index, so jobs whose seeds differ by a fixed offset do not share rollout keys. Earlier runs are engineering diagnostics, not valid independent-rollout
evidence. An [intermediate key-split check](../research/t2/run-smoke-2026-10-15-split-keys/report.json)
had two uniform-reward groups; that result is retained as well. The current run
captures its source bytes before execution.

The scoring change was made after seeing the first outcome. These are engineering
checks, not preregistered study results. The two scores are not a measured learning
gain. No baseline comparison, noise floor, independent-seed confirmation, held-out
test, CUDA test, or 1.5B training result is claimed. The separate
[Mac correctness evidence](../research/t2/backend-correctness-namespaced-2026-10-15.json)
checks the MLX and PyTorch numerical adapters on tiny models.

The shared receipt helper changes T1/T3 adapter and evaluator hashes. Frozen data,
training programs, and historical evidence are unchanged. Old cache identities
cannot alias the new adapter versions.
