# T3: data mixtures

Implemented on October 15, 2026. Supports N1, N4, and N9 in [NEEDS.md](../NEEDS.md).
The [adapter](../src/openloop/loops/t3.py) uses the same `ExperimentEnv`, ledger,
executor, token budgets, and BPB evaluator as [T1](LOOPS.md#t1-autoresearch-mlx).
It adds no storage tables or dependencies. Importing it starts no work.

## Frozen inputs and mutable weights

Construct `T3(training, sources, training_config=...)` with a configured T1 and a
named catalog of frozen `Corpus` snapshots. The T1 corpus supplies validation.
Every catalog entry supplies only its train membership. These snapshots may
contain different public corpora, but all must use the existing FineWeb-format
manifest and exact-content split policy. This task does not download or freeze
another corpus. Preparing a new source is a separate, reviewed data task.

Only `weights` is mutable within a T3 loop. Supply every source name with a
nonnegative integer ratio and at least one positive value. Zero disables a
source. Ratios are reduced by their greatest common divisor, so `1:3` and `2:6`
have the same candidate identity. Fractions, booleans, unknown names, and negative
weights are rejected. An identical snapshot cannot have two source names.
Source order and machine-specific paths do not affect identity.

`training_config` fixes the architecture and optimizer settings for that loop.
It uses T1's normalization and protected-setting checks. Omitting it selects the
shared recipe's defaults. It is not part of the weight-search surface. To test a
combined architecture and mixture, construct a new T3 with those fixed training
settings and record both selected parents in `ExperimentEnv(parents=...)`.
The combination still needs independent verification.
Fixed architecture changes create a new comparison context. The current decider
does not pair results across those contexts; an S5 factorial comparison requires
its own trusted comparison path. Ordinary weight candidates within one T3 share
a context and can use the existing decider.

The catalog, validation snapshot, recipe, fixed training configuration, adapter,
tokenizer, and evaluator enter the specification. The normalized weights, seed,
phase, and fidelity enter each experiment. Changing any of them prevents an
incompatible cache hit. Cache aliases remain references to earlier samples;
explicit `Purpose.REPLICATION` starts a new attempt.

## Token allocation

Weights apply to **trained tokens**, in whole device microbatches of
`DEVICE_BATCH_SIZE * 2048` tokens. They do not apply to document counts.
The fidelities remain 8,388,608 and 20,971,520 training tokens. T1 checks that
batch sizes divide those budgets.

For K microbatches, allocate `floor(K * weight / sum(weights))` to each source.
Assign the remainder to the largest fractional remainders; seed-and-source hash
order breaks ties. Smooth weighted round robin interleaves these finite quotas
with the same deterministic tie order. Each source's rounded allocation differs
from its ideal share by less than one microbatch. Tiny positive weights can
therefore receive zero tokens. `loop.token_allocation(inputs)` reports the exact
allocation before admission. A seed changes ties, not a random document shuffle.

Each source has a private instance of the unchanged upstream token packer.
It repeats that source's frozen document order and retains upstream BOS alignment,
cropping, and full token utilization. It never mixes validation into training.
Epoch labels belong to the selected source; they are not global mixture epochs.
The training source prefetches one batch after its final update; the mixture
loader returns its last batch once more for that unused prefetch. This adds no
trained tokens and does not consume an extra source batch.

The worker measures delivered source tokens and checks them against the complete
allocation. The evaluator requires that receipt as well as T1's token, step,
evaluation-budget, and executor checks. The ledger result records
`mixture_tokens/<source>` observations in tokens, including zero counts. The
primary metric remains `val_bpb`; source counts do not become quality metrics.

## Shared ledger example

This code constructs a loop and job without executing training. `training` is
an existing T1; `additional` is a separately frozen, compatible `Corpus`.

```python
from openloop.loops import T3, ExperimentEnv, LoopAction

mixture = T3(
    training,
    {"fineweb_edu": training.corpus, "additional": additional},
    training_config={"DEPTH": 6},
)
config = mixture.normalize_config({"weights": {"fineweb_edu": 3, "additional": 1}})
inputs = mixture.spec.inputs(config, LoopAction(seed=42), environment_hash)
job = mixture.build_job(inputs)
allocation = mixture.token_allocation(inputs)

env = ExperimentEnv(
    mixture,
    ledger,                       # The same Ledger instance used by T1.
    runner=mixture.run,
    config=config,
    environment_hash=environment_hash,
    budget=8_388_608,
    parents=(architecture_run_id, mixture_run_id),
)
# Only an explicit, separately approved `await env.step(...)` executes training.
```

The coordinator supplies real environment identity and existing parent run IDs.
T1 and T3 use distinct loop identities in the same ledger; results cannot alias
across loops. The caller owns the shared executor and retains its logs. The same
GPU lane, resource limits, cancellation, and failure logging apply to both.

## Trust boundary and limits

The worker reconstructs its catalog from host-supplied paths, verifies the job
against the pinned snapshots, and checks every manifest, membership digest, and
raw shard size before training. Every selected text is checked against its frozen
digest and content-split assignment before tokenization. The common content-hash
policy prevents an exact validation or held-out text from entering train even
when it appears in another corpus. It does not detect near duplicates or broader
semantic contamination. Duplicate train texts across distinct corpora can repeat.

Held-out membership files are never opened. Raw shards may contain all splits;
the reader only yields the requested membership. As with T1, this is reviewed
local execution, not a filesystem sandbox. Held-out scoring and release require
a separate trusted host path; this adapter does not implement native held-out
evaluation. No S5 result follows from constructing a combined candidate.

The [tests](../tests/loops/test_t3.py) exercise both fidelities through CPU-only
workers, actual source selection, a shared ledger and lineage, cache reuse,
replication, protected settings, corrupt sources, split leakage, and absent
held-out files. [Property tests](../tests/loops/test_mixture.py) check finite quota
conservation, rounding, scale invariance, and order stability. These checks do
not establish native MLX behavior, throughput, a noise floor, or a mixture gain.

The shared process adapter and worker extension change T1's adapter/evaluator
identity. Frozen training bytes, program hashes, data manifests, and historical
evidence remain unchanged. Earlier T1 cache entries cannot substitute for new
adapter identities. No native T3 training was run for this implementation.
